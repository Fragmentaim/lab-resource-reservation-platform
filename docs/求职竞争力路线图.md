# 实验室资源预约平台：求职竞争力路线图

## 项目定位

目标不是再做一个通用后台或聊天 Demo，而是构建一个能在后端实习面试中完整讲清楚的项目：

> 面向实验室资源预约的高并发业务系统，结合可靠异步处理、可追溯 RAG 和受权限控制的 AI 工具调用。

它必须同时展示：业务建模、并发与一致性、消息可靠性、AI 工程化、可观测性和可验证性。

## 分阶段能力路线

### Phase 0：Git 与可复现基线

- `feature/knowledge-rag-module`：已验证 RAG 前端接入的稳定锚点。
- `feature/rag-workbench-upgrade`：知识库工作台和后续能力的开发分支。
- 每个功能只在以下条件满足后提交：`git diff --check`、后端 `mvn test`、前端 `npm run build`；涉及接口时补真实 HTTP 验证。
- 提交按单一能力拆分；禁止把运行日志、模型、密钥、上传文件或 IDE 文件加入 Git。
- 同步远端前先检查 `ahead/behind`；有本地工作时不强行 rebase 或覆盖远端。

### Phase 1：可解释 RAG 工作台

- 会话列表、新对话、历史恢复、软删除。
- 回答依据卡：文档标题、页码、分块片段、检索方式和相关度。
- 检索证据检查器：点击引用后查看实际用于回答的上下文。
- 管理端文档运营：处理状态、分块数、失败重试、标签与分类。
- 价值：回答“模型为什么这么回答”时有数据和页面证明，而非只展示聊天框。

### Phase 2：GPU 本地检索能力

本机是 RTX 4060 Laptop GPU（8GB），优先选择可稳定同机运行的 0.6B 方案，而不是盲目加载 4B/8B 模型：

- Embedding：`Qwen/Qwen3-Embedding-0.6B`，中文/多语言，最大 1024 维，模型文件约 1.2GB。
- Rerank：`Qwen/Qwen3-Reranker-0.6B`，与 Embedding 同系列。
- 运行策略：GPU 优先、显存不足自动转 CPU；保留关键词检索与远程模型模式作为降级路径。
- 交付：模型下载脚本、显存探测、健康检查、批量入库、重建索引、性能测试报告。

当前已完成 Embedding 与 Reranker 的本机验收：模型权重、缓存、临时目录均落在 `D:\AI-Models`；
`scripts/verify-rag-embedding.py` 在 RTX 4060 Laptop 上确认输出 `3 x 1024` 向量，加载并编码耗时约 1.86 秒。
`scripts/verify-rag-reranker.py` 通过实际运行的本地 GPU Reranker HTTP 服务验收相关候选排序，避免用通用分类头替代 Qwen3 的官方 yes/no logits 评分协议。
`scripts/download-rag-models.ps1` 会校验 C/D 盘余量，并通过可续传下载保护大文件传输。Reranker 与检索效果对比留待评测阶段实施。

### Phase 3：RAG 质量评测

- 建立至少 30 条实验室领域问答样本，标注正确文档或分块。
- 记录 Recall@K、MRR、无答案拒答率、端到端延迟和人工正确率。
- 对比关键词检索、向量检索、混合检索、重排四种配置。
- 将每次实验参数、模型版本、结果和结论写入评测报告。

### Phase 4：Java 受权限控制的 AI 工具调用

AI 不能直接操作数据库；由 Java 后端暴露受控工具，并复用当前用户身份：

- `queryMyReservations`：查询当前用户预约。
- `findAvailableSlots`：查询资源可预约时段。
- `getReservationPolicy`：优先检索知识库中的规则。
- 先只读，完成权限与审计后再评估“创建预约”类写操作。
- 每次工具调用记录 traceId、用户、参数摘要、耗时和结果状态。

当前已落地三项受控工具：

- `GET /knowledge/tools/reservation-context/me`：仅以当前登录用户身份返回只读预约摘要与至多 3 条待使用预约。
- `GET /knowledge/tools/reservation-context/users/{userId}`：仅管理员可调用；服务层仍会再次校验，防止未来非 HTTP 调用绕过权限。
- `GET /knowledge/tools/resource-availability`：基于资源状态、时段开放状态、未来时间和剩余名额筛选可预约时段，返回最小化资源字段。
- `GET /knowledge/tools/cancellation-preview/{reservationId}`：只预检本人预约是否可取消，返回明确的确认提示；不替用户执行取消写操作。
- 返回模型刻意不包含手机号等无关个人信息；智能问答页面以 `READ ONLY` 卡片展示该受控上下文。
- 每次调用写入 `ai_tool_call_log`：traceId、调用者/目标用户、授权作用域、最小参数摘要、耗时和结果均可由管理员分页查询；审计失败不会阻断只读工具。
- 已将三项受控工具接入原生 LLM Function Calling：AI 服务通过 OpenAI-compatible `tools/tool_calls` 仅生成调用计划；Java 负责白名单、参数校验、身份权限、实际执行与审计，并将结果回传模型完成多轮回答。仍不让模型直接访问数据库，也不开放无确认写操作；规则路由仅作为网关异常时的安全回退。

### Phase 5：演示与求职材料

- 补充架构图：预约主链路、Outbox/MQ、RAG 检索、Tool Calling 权限边界。
- 准备 3 分钟演示剧本：热门预约、文档入库、引用问答、查询我的预约。
- README 增加本地启动、模型配置、测试结果、性能数据与关键技术取舍。
- 简历重点写可量化结果，例如测试覆盖、检索指标、端到端延迟和可靠投递策略。
